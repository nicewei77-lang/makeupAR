# Eyebrow AR Rendering Design

Status: MediaPipe canonical asset standard linked; live landmark bridge implemented
Date: 2026-06-30
Related product doc: `docs/product/eyebrow-makeup-feature.md`

## Current System

The current app sends React Native recipe batches to Unity through `RNBridge`.
Unity parses region layers and applies them through `E3RegionMaskOverlay`, which
renders a smooth UV mask over the AR Foundation `ARFace` mesh. Existing runtime
regions are now `lip`, `cheek`, `eye`, and `brow`.

The renderer already supports:

- Per-region enabled state.
- Color, opacity, intensity, feather, coverage, roughness, specular, gloss, and
  gradient fields.
- Mask textures in `Assets/Resources/SmoothRegionMasks/`.
- ARFace mesh/UV attachment.
- Visibility suppression for clean/capture/debug modes.
- Tracking-state fade/hide behavior.

## Implemented First Loop

Eyebrow support was added by extending the existing region recipe pipeline:

1. Extend region constants from `lip | cheek | eye` to include `brow`.
2. Add brow texture sample presets such as `natural_brow` and `soft_brow`.
3. Add brow mask texture ids for the local candidates.
4. Generate an in-house 512x512 brow UV mask under
   `unity/MakeupARUnityValidation/Assets/Resources/SmoothRegionMasks/`.
5. Teach Unity parsing and mask normalization to accept `brow`.
6. Route `brow` to the current `smooth-region-mask` renderer for this loop.
7. Record the renderer routing contract so future dedicated renderers can
   replace the implementation per region.

Implemented contract values:

| Field | Value |
| --- | --- |
| Region | `brow` |
| Renderer mode | `smooth-region-mask` |
| Mask texture id | Default `brow-png-natural-hair-v1`; user-facing options include `brow-png-dailyflat-hair-v1`, `brow-png-dailyflat-sharp-v1`, `brow-png-dailyflat-multiply-v1`, `brow-back-arch-soft-mix-v1`, `brow-slim-tail-fine-hair-v1`, `brow-png-daily-hair-v1`, `brow-png-natural-hair-v1`, `brow-png-narrow-hair-v1`, and `brow-png-lightbrown-hair-v1`; compatibility resources `brow-soft-arch-fine-hair-v1` and `brow-drawn-mask-v1` |

## Canonical Asset Coordinate Standard

As of 2026-06-30, the app-wide source coordinate standard for authored makeup
assets is the MediaPipe/ARCore canonical face texture canvas. PSD-derived lip,
cheek, and brow resources are generated by downsampling the authored full
canvas into the runtime mask texture; they are no longer bbox-fitted into
ARKit/Unity mask bboxes. ARKit `ARFace` UV resources and procedural brow PNG
candidates remain legacy comparison and runtime-compatibility resources, not
the authoring standard for new assets.

This coordinate decision does not by itself recognize the user's live eyebrow.
It only defines where asset pixels live in the canonical face canvas. Live
placement still needs detector landmarks to map the canonical asset region onto
the current face.

## Renderer Routing Contract

The stable contract should be the recipe region, not a specific renderer class.

Implemented route table:

| Region | Current renderer id | Backend | Future renderer option |
| --- | --- | --- | --- |
| `lip` | `lip-smooth-region-mask-renderer` | `E3RegionMaskOverlay` | `LipMakeupRenderer` |
| `cheek` | `cheek-smooth-region-mask-renderer` | `E3RegionMaskOverlay` | `CheekMakeupRenderer` |
| `eye` | `eye-smooth-region-mask-renderer` | `E3RegionMaskOverlay` | `EyeMakeupRenderer` |
| `brow` | `brow-smooth-region-mask-renderer` | `E3RegionMaskOverlay` | `BrowMakeupRenderer` |

The first loop now has code-level routes and diagnostic `rendererId` output,
while all rows still use the existing smooth-mask backend. A full class split
should wait until the brow path is working on device or until an implementation
change requires it.

## Why Not Split All Renderers Now

`E3RegionMaskOverlay` currently holds region application, mask loading,
diagnostics, material configuration, tracking visibility, and lip-specific
features. Splitting all renderers is a good future direction, but doing it in
the same loop as the first eyebrow feature would increase regression risk for
already tuned lip matte/gradient/gloss behavior.

The safer path is:

1. Add brow through the existing renderer.
2. Keep tests around region parsing and recipe payload shape.
3. Verify brow on device.
4. Split renderers in a separate refactor when there is a working visual target
   to preserve.

## Brow Mask Strategy

The first brow mask is generated in-house and procedural. It is a
soft, symmetric eyebrow shape in ARFace UV space, stored as a readable,
uncompressed Unity resource. It favors conservative coverage so it does not
paint the forehead or eyelids.

Initial installed mask QA showed the shape followed the face correctly but
looked like `^ ^`: each brow's center was too high, the mask was far too thick,
and the effect read as sticker-like. The tuned mask keeps the same resource id
and renderer contract, but flattens the arch and reduces the stroke footprint.

The user chose to skip rebuilding the intermediate flatter mask and continue
into the next local loop. A local variation catalog was generated, and three
options were selected for the app: soft arch with fine hair, back-shifted arch
with soft mix texture, and slim tail with fine hair. The first is the RN/Unity
default for the next QA build; the old `brow-drawn-mask-v1` remains available
for comparison.

The first three-option device QA confirmed tracking and expression attachment,
but the brows were too faint, too centered, and slightly below the real brow
line. The current local post-QA candidate masks are shifted `10px` outward per
side and `7px` upward without increasing thickness. This post-QA tuning has now
been rebuilt into `UnityFramework.framework`, installed, and launched on
`CloudsiPhone (26.5)`; visual acceptance on the rebuilt app is still pending.

Follow-up QA on that rebuilt app confirmed `spread=` and `y=` are visible and
adjustable, but the renderer id was too buried in the long recipe summary, the
brow remained too centered, too faint, and the visible angle still read as an
angry/upward brow. The next local candidate therefore switches the default to
the flatter `brow-back-arch-soft-mix-v1`, removes the higher-arch and legacy
masks from the user-facing picker, starts brow spread at `0.20`, expands the
spread clamp to `±0.34`, raises default opacity/intensity to `0.75`, and
increases Unity brow alpha scaling so `75%` should be readable and `100%`
should be intentionally strong.

The mask remains a single-channel soft alpha texture, but no longer uses a
fully uniform central ridge. If later device QA still shows poor fit, later
loops can add:

The current PNG hair loop adds user-authored brow art as generated mask/detail
resources rather than applying the original PNGs directly. The generator removes
the grey background and glow, maps the left/right brow art into the same 512 UV
space, stores soft shape alpha in red/alpha, and stores extracted hair strokes
in blue. The shader keeps the existing color layer and uses `_DetailAmount` to
darken/detail only the hair signal inside the mask. This gives a controlled
multiply-like effect without multiplying the full grey source image over the
face.

The current local renderer treats brow as a fiber-first special case inside the
shared shader. `_BrowPhotoDetailMode` no longer uses the full brow shape as the
main rendered mask. Instead, `BrowFiberAlpha` high-passes the blue detail
channel against its softened neighborhood, uses the red channel as a gate, and
keeps the red shape contribution as a very weak powder veil. This is different
from lip and cheek, where broad smooth-region fill is the desired behavior.

PSD semi-arch is the exception inside the brow photo-detail path because its
PSD layers have distinct product meanings. The runtime texture stores
`full` in red as the target brow core/protection mask, `gradient` in green as a
very light powder layer, and `left/right` in blue as the hair-detail layer.
Unity binds `_BrowPowderFill=1` only for `psd-arcore-brow-semi-arch-v1`; in that
mode the pigment pass reads powder from green, keeps hair from blue, and leaves
red available for target-core cleanup protection rather than using red as a
filled makeup region.

The PSD intake follows the same mask-first rule. White or gray PSD artwork is
treated as tintable coverage and density data, never as baked white makeup
color. Runtime pigment still comes from `_RegionColor`, which RN derives from
the selected lip, cheek, or brow color parameters. Because the supplied PSD uses
an ARCore/MediaPipe canonical-face texture layout, the generator now preserves
that full-canvas layout for all PSD-derived lip, cheek, and brow masks instead
of squeezing those layers into ARKit/Unity-specific target boxes. PSD semi-arch
brow still keeps `full`, `gradient`, and `left/right` in separate runtime
channels so the cleanup pass can treat "recognized/source brow outside full" as
skin restoration while the pigment pass keeps hair and powder separate.
The 2026-06-30 PSD update also expanded cheek intake from one under-eye source
to seven selectable blush shapes: `undereye`, `asia-z`, `sunkissed`,
`daily-oval`, `undereye2`, `lovely-round`, and `lifted-diagonal`. The extractor
matches runtime PSD layer paths case-insensitively because Photoshop group
capitalization changed from `semi-arch` to `Semi-arch`, and cheek sources now
arrive as `Root/blush/<style>/all` layers.

Device feedback on 2026-06-30 made the coordinate failure explicit: a PSD brow
texture can be authored against a MediaPipe canonical target and still appear in
the wrong place if the renderer simply samples that texture with ARKit `ARFace`
UVs. That is not brow recognition; it is only static texture sampling. Do not
hide this mismatch with PSD-only shader constants or per-asset y/gap/scale
offsets. The product direction is to keep the asset in canonical-face space and
drive the live brow placement from detector output: Apple Vision eyebrow
landmarks on iOS, and MediaPipe Face Landmarker/canonical landmarks when that
runtime dependency is deliberately added. Runtime camera frames must stay
transient in memory; only landmark points and diagnostics may be logged.

## Brow Landmark Runtime Privacy Contract

User approval recorded on 2026-06-30: MediaPipe Face Landmarker may be added as
an on-device brow placement runtime for the eyebrow feature. The expected model
artifact is an app-bundled `face_landmarker.task`; the app must not download a
model or send inference frames to a server at runtime.

Installed dependency state on 2026-06-30: iOS links `MediaPipeTasksVision`
`0.10.14` through CocoaPods, bundles `face_landmarker.task` in the app target,
and includes a Swift runtime that imports `MediaPipeTasksVision`, resolves the
bundled model path, runs Face Landmarker on transient in-memory PNG input, and
returns eyebrow landmark/bbox diagnostics through app-owned C ABI symbols
`E7MediaPipeAppDetectBrowLandmarksPng` and
`E7MediaPipeAppReleaseCString`.

Bridge state on 2026-06-30: Unity owns `E7MediaPipeBrowLandmarkRuntime`, which
captures a transient frame only while brow is active. UnityFramework exports
the Unity-facing `E7MediaPipeDetectBrowLandmarksPng` and
`E7MediaPipeReleaseCString` symbols from an Objective-C++ bridge plugin, then
resolves the app-owned Swift symbols with `dlsym`. This keeps UnityFramework
linkable as a standalone framework while the RN app target owns the Swift
MediaPipe dependency. Unity forwards an `e7_mediapipe_brow_landmarks` event to
React Native; RN formats point counts, bbox, confidence, latency, and explicit
privacy flags in the HUD. This is a live landmark diagnostic bridge, not yet
the final brow placement/warp renderer.

Detector input frames are not product media. For landmark detection, raw camera
frames are memory-only and must be released after analysis. Policy keyword:
raw camera frames are memory-only. The detector path
must not write raw frames, intermediate screenshots, PNG/JPG dumps, videos, or
camera buffers to disk, Photos, evidence folders, logs, or network services.
Detector diagnostics may contain only landmark, bbox, confidence, timing, and
status numbers. Policy keyword: landmark, bbox, confidence, timing, and status numbers only.
They may not contain raw pixels, encoded images, thumbnails, or face screenshots.

The user-triggered product capture exception is separate: when the user taps
`Save Photo`, `Record Video`, or a future explicit capture control, the app may
save the final AR makeup result locally to Photos through the existing
add-only Photos permission. That user action does not authorize background raw
frame retention for detector debugging.

The PSD semi-arch source can still look filled if the `left/right` channel is
treated as broad density. The generator therefore preserves the direct
user-drawn hair strokes as the blue detail channel, keeps `gradient` as a weak
powder channel, avoids MaxFilter-style stroke widening, and preserves the
authored full-canvas MediaPipe/ARCore canonical position instead of stretching
each brow side into a runtime target box. RN gives this PSD mask its own
detail/cleanup defaults instead of reusing the generic PNG hair placement
preset.

The 512 Unity brow textures are now considered the minimum runtime size, not
the desired source-art size. New photo-like brow assets should arrive as six
single-side transparent PNG masters: three styles times wearer-left and
wearer-right. Each master should use a consistent `2048x1024` canvas, straight
alpha, sRGB, no baked face/background/glow/shadow, and enough transparent
padding that the crop baseline is identical across all six files. The brow
itself should occupy about `1500..1700px` width and `220..360px` height, with
individual strokes around `6..12px` in the master so they survive downsampling.
The next generation pass should produce a `1024x1024` Unity brow atlas for
quality QA, and keep the current `512x512` atlas only as a performance fallback.

For bright PNG brows, RN now sends `normal` composition when the selected brow
color is `light_brown`; darker PNG brows keep `multiply`. This keeps light brow
color from being crushed by the destination-color multiply pass while preserving
hair texture through `_DetailAmount`.

The 2026-06-28 feedback retune changes the local default from the flat probes
to `Natural hair` (`brow-png-natural-hair-v1`) because it was the most readable
non-hollow baseline. The flat probes are shorter and denser so they no longer
read as three straight disconnected strokes. `Soft flat` and `Slim tail fine`
remain available but have boosted procedural visibility, with `Soft flat`
top-edge softened so it stays flatter.

The later FLAT follow-up keeps the same Unity/RN shader path for all PNG brow
masks, but removes the visual mismatch caused by FLAT-specific image
post-processing. `Daily flat`, `Flat sharp`, and `Flat multiply` now remap their
alpha/detail from the extracted hair-detail signal so they respond like
`Daily hair`, `Natural hair`, and `Narrow hair` instead of reading as solid
strips.

- Separate left/right channels.
- Asymmetry parameters.
- Dedicated brow mesh culling.
- Dedicated brow shader for hair-density or powder-fill behavior.
- Optional landmark or Apple Vision anchor provider after explicit privacy
  review and user approval.

## Material Strategy

First-loop brow should avoid glossy or glitter behavior. Use low specular,
moderate feather, multiply behavior for darker brows, and normal alpha behavior
for the bright PNG `light_brown` path. Brow now has its own mask policy inside
the shared smooth-mask backend: threshold `0.035`, default feather `0.42`, and
recipe feather clamped to `0.34..0.48`. The RN defaults now use the
MediaPipe/ARCore canonical PSD masks for lip, cheek, and brow. Brow starts from
neutral placement deltas (`maskSpreadX=0`, `browGap=0`, `maskOffsetY=0`) so
asset alignment issues are not hidden behind per-mask baseline offsets.
`soft_brow` is deliberately distinct: lower intensity, lower coverage, higher
feather, and lower default detail so the UI can label it `Soft Powder`. The
brow color palette is separate from lip colors: `ash_brown`, `neutral_brown`,
`dark_brown`, `soft_black`, and `light_brown`. RN exposes brow-only
`Temperature` and `Depth` sliders. These compute a final HTML hex color on the
RN side and keep sending it through the existing Unity `color` field, so no
Unity recipe schema change is required for color QA.
PNG hair detail is separate from color: RN sends `detailAmount`, Unity stores
it in `RegionRecipeState.DetailAmount`, and `SmoothRegionMask.shader` exposes
`_DetailAmount` to add softened extracted hair strokes after the chosen brow
color is applied.
RN also exposes brow-only `Gap`, `Brow Y`, `Angle`, `Arch`, and `Arch Position`
placement
sliders. `Gap` is the user-facing midline spacing control; RN sends it as both
`maskSpreadX` and `browGap` so older Unity spread logic and the new brow-specific
diagnostics stay aligned. `Brow Y` becomes signed `maskOffsetY`, `Angle` becomes
signed `browAngle`, `Arch` becomes signed `browArch`, and `Arch Position`
becomes signed `browArchPosition`. `RNBridge` and `E3RegionMaskOverlay` clamp
these to `±0.34` for gap/spread, `±0.08` for vertical offset, `±0.16` for
angle, `±0.05` for arch, and `±0.15` for arch position. The shader applies gap
through `_MaskSpreadX`, vertical offset through `_MaskOffset.y`, and the
angle/arch sampling warp through `_BrowAngle`, `_BrowArch`, and
`_BrowArchPosition`.

RN keeps placement sliders as user-facing deltas. Unity also smooths brow
overlay mesh vertices with a conservative local vertex low-pass filter. The
ARFace transform still follows the tracked face directly, while only brow local
mesh deformation is stabilized to reduce subtle surface jitter on thin hair
strokes.
The current brow reshape path is deliberately a middle option: no AI
segmentation, no face-frame storage, and no full inpainting. RN sends
`browCleanupEnabled`, `browCleanupStrength`, and `browReshapeStrength`;
`RNBridge` and `E3RegionMaskOverlay` clamp the strengths to `0..1`. When
`browCleanupEnabled=false`, Unity forces cleanup strength to `0`, source mode to
`none`, and skips the cleanup pass and ARCameraBackground fallback request while
leaving the brow pigment/reshape path available. The shader keeps the existing
brow pigment pass, adds a target-mask reshape boost inside the brow ROI, and
runs a very low-alpha `BrowCleanupConcealer` pass when skin restoration is
enabled. The cleanup alpha is now the union of a target-mask halo and internal
`_BrowCleanupSourceTex`, which is bound from
`SmoothRegionMasks/brow-cleanup-source-v1` and sampled in original face UVs
instead of the target brow's shifted/warped UVs. This keeps source cleanup over
the user's original brow even when `Brow Y`, `Gap`, or arch controls move the
selected asset elsewhere, while protecting the newly drawn target-brow core from
source cleanup overpaint. The current cleanup pass does not paint a fixed beige
concealer color in the pigment pass. It uses a built-in-renderer `GrabPass`
named `_BrowCleanupFrameTex`, samples farther surrounding pixels from the current
AR camera composite, downweights dark brow-hair samples, and blends that
weighted live-frame skin estimate into the cleanup halo. This can soften
original eyebrow hairs that peek around a new asset, but it is still not a true
semantic removal pass. A second QA-only source mode is now prepared:
`browCleanupSourceMode=ar_camera_background` asks Unity to render
`ARCameraBackground.material` into a transient GPU `RenderTexture` with
`Graphics.Blit`, bind it as `_BrowCleanupCameraTex`, and switch
`_BrowCleanupFrameSource` only when that texture is available. The product
default remains `grabpass`; the fallback does not store, log, or upload camera
frames.
Unity `recipe_applied` events include `browCleanupEnabled`,
`browCleanupSource`, `browCleanupFallback`, `browCleanupStatus`, and
`browCleanupSourceMode`; the expected default candidate values are `true`,
`grabpass_live_frame_skin_sample`, `ar_camera_background_texture`,
`grabpass_candidate`, and `grabpass` when brow cleanup is enabled. For the AR BG
mode, Unity also reports
`browCleanupFallbackAvailable` and the transient texture size through
`browCleanupCameraTextureWidth`/`browCleanupCameraTextureHeight`; this confirms
whether the material blit path was actually ready without exposing raw frame
data.
Coverage and feather remain visible for brow editing because they map directly
to density and edge softness. Lip/material finish controls such as roughness,
specular, glossy, gradient, normal, and overlip should be hidden while brow is
focused.
For QA, raise opacity first, intensity second, and coverage last to improve
visibility without immediately making the brow sticker-like; use `Temperature`
and `Depth` to fine-tune color after visibility is readable, then use `Gap` for
brows that are too centered or too wide, `Brow Y` for vertical placement,
`Angle` for an angry/upturned pose, `Arch` for localized brow mountain height,
and `Arch Position` when only the brow mountain needs to move forward/back
before generating another mask texture.

## Local Capture

Product photo/video capture is separate from validation evidence capture. RN
calls the native `MakeupARLocalMedia` module only from explicit user actions in
clean mode. `capturePhoto` renders the current app window and saves the final AR
view to Photos through add-only photo-library permission. `startVideoRecording`
and `stopVideoRecording` use ReplayKit plus `AVAssetWriter`, then save the
resulting local movie to Photos. The module does not use networking APIs and
does not upload captured media.

The QA panel now treats `RAW`, `PROCESSED`, and `FINAL` as debug view stages
instead of product mask candidates. `LEGACY DRAWN` remains a compatibility
resource only and must not be surfaced in the user-facing QA controls.

The shader does not need a new third-party dependency. If the generic shader
cannot create a convincing brow result, a dedicated brow shader can be added in
a later renderer split.

## React Native Data Flow

React Native should add `brow` to the same payload builder that currently
emits region layers. The Unity bridge should continue to receive a batch with
one layer per known region. The important compatibility point is that future
Unity code can decide renderer selection internally from `region` and
`textureSample`.

No raw camera frame storage, upload, recommendation, commercial SDK, or Android
work is part of this flow. The only approved model-inference exception is the
on-device MediaPipe brow landmark runtime described in the privacy contract
above.

## Future Renderer Split

When the feature is stable enough to preserve, split by responsibility:

- Common recipe schema and validation.
- Common face tracking visibility state.
- Per-region renderer classes.
- Per-region material/shader policy.
- Per-region mask and diagnostic policy.

This split should be tested as a refactor, not mixed into the first visible brow
implementation unless the existing renderer blocks progress.
